### Data Flow

1. **Event Source**: X11 events (touch, expose) → `Display.event_tx` → mpsc channel
2. **Event Processing**: `App::run()` loop receives events, delegates to top `Screen`
3. **Screen Response**: Returns `Transition` enum controlling navigation
4. **Async Work**: Screens spawn `tokio::spawn` tasks, post results as `AppEvent` via `display.event_tx`
5. **Render**: Screens borrow `Display.renderer` to draw; double-buffering via x11rb

### Key Typestate Pattern: BoardAPI

```rust
// Typestate markers control API surface availability
pub struct Idle;           // Authed, no game scoped
pub struct InGame;         // Specific game active

pub struct BoardAPI<S> {
    pub token: TokenInfo,
    pub user: LichessUser,
    pub state: S,
}
// move_piece/resign/abort/stream only available when S = InGame
```

## Conventions (Observed)

### Error Handling

- **Pattern**: `Result<T, Box<dyn std::error::Error>>` throughout
- **Strategy**: Errors caught at screen level, logged via `log::error!`, return `Transition::Stay`
- **Async Context**: Non-`Send` `Box<dyn Error>` converted to `String` before crossing await boundaries
- **Example**: `api/api.rs` maps errors to String to maintain `Send` compatibility
- **Global Handler**: None — errors handled locally with logging, no panic recovery

### API Design

- **Protocol**: REST/JSON over HTTPS
- **Base URL**: `https://lichess.org/api` (compile-time constant)
- **Casing**: snake_case for Rust structs, camelCase for JSON via `#[serde(rename_all = "camelCase")]`
- **Authentication**: Bearer token in Authorization header
- **Response Handling**: Direct `reqwest::Response.json()` deserialization to typed structs
- **Retry Logic**: Transparent fallback — authenticated puzzle/next retries anonymously on 403

### Type Safety

- **Strong Typing**: Extensive use of enums (Color, Piece, DrawColor, Turn, etc.)
- **Typestate**: `BoardAPI<Idle>` vs `BoardAPI<InGame>` — compiler enforces correct API usage
- **No `unsafe`**: Codebase appears to be 100% safe Rust
- **Send/Sync**: Careful handling of async boundaries, `Arc<Mutex<T>>` for shared state

### Observability

- **Logging Framework**: `log` crate with `log4rs` for file output, `env_logger` for stdout
- **Log Levels**: `error!`, `warn!`, `info!`, `debug!` used appropriately
- **Log Destinations**: 
  - Debug builds: stdout via `env_logger`
  - Release builds: `log/app.log` via `log4rs::FileAppender`
- **Build Metadata**: Git SHA and timestamp baked into binary, logged at startup
- **No Metrics**: No structured metrics, health checks, or tracing beyond logging

### Testing

- **Test Suite**: None — no `#[test]` modules found
- **Quality Assurance**: Manual testing via `run-dev.sh` and on-device deployment
- **Validation**: Compile-time checks, runtime logging, no unit/integration tests

### Async Patterns

- **Runtime**: `#[tokio::main]` on main function
- **Task Spawning**: `tokio::spawn` from within event handlers
- **Result Communication**: `oneshot` channels for OAuth flow, `mpsc` for event loop
- **Timeout Handling**: `recv_timeout` on event channel for periodic redraws

### UI Rendering

- **Coordinate System**: Absolute pixels, hardcoded for 1072×1448 (Kindle Paperwhite 4)
- **Double Buffering**: x11rb auto-flushes, but Renderer uses put_image for full-frame updates
- **Partial Rendering**: BoardWidget diffs current vs last position, only repaints changed squares
- **Color Model**: `DrawColor` enum (Black, White, Gray, DarkGray, LightGray) mapped to X11 pixel values
- **Font**: Embedded AdwaitaSans-Regular.ttf, loaded once at Renderer construction

### OAuth Flow

1. `local_ip_address::local_ip()` discovers host LAN IP
2. Axum server started on `0.0.0.0:<redirect_port>/callback`
3. PKCE challenge/verifier generated, QR code with auth URL displayed
4. User scans QR with phone, Lichess redirects to callback
5. Axum extracts code, exchanges for token via OAuth2 client
6. Token persisted to `secrets/token.json`
7. Server shuts down, `AuthSuccess` event posted

### Update Flow

1. `check_for_update()` queries GitHub releases API
2. Compares semver against `version::current()`
3. If newer: downloads, verifies SHA256, stages to `bin/kindle-hello.new`
4. `chess_app.sh` moves `.new` to final path at launch (while no instance running)
5. UpdateScreen displays progress and result

## Signals / Active Considerations

### Consistency Gaps

1. **No Test Suite**: Zero automated tests — all validation is manual. Adding even basic unit tests for bitboard logic would catch regressions.

2. **Mixed Error Types**: Some paths use `Box<dyn Error>`, others use `String`. The async boundaries force String conversions, creating inconsistency.

3. **Hardcoded Dimensions**: Screen layouts use absolute pixel coordinates (1072×1448). No abstraction for different Kindle models or orientations.

4. **Debug vs Release Divergence**: 
   - Debug: Pointer motion events enabled, window manager handles cursor
   - Release: `override_redirect(1)` for full-screen, no cursor
   - Different event masks could cause subtle behavior differences

### Debt Hotspots

1. **`models/ui.rs`**: Contains Display struct, Screen trait, AND all Screen struct definitions. At ~700+ lines, this violates single responsibility. Screens should live in separate files under `ui/screens/`.

2. **`ui/screens.rs`**: Contains `impl Screen for ...` for ALL screens. At ~1200+ lines estimated, this is a maintenance burden. Each screen's impl should be co-located with its struct definition.

3. **`ui/widgets/board.rs`**: Complex widget with piece sprite loading, position diffing, move highlighting, flip logic. At ~440+ lines, could benefit from decomposition.

4. **`api/oauth.rs`**: OAuth2 client construction is verbose with many type parameters. Could be simplified with type aliases or a builder pattern.

5. **`models/board_api.rs`**: Stream event handling and game state management is complex. The `InGame` struct holds redundant data (initial_board + board).

### Integration Points

1. **Lichess API**: Full integration for puzzles, ongoing games, game stream events. Missing: challenge creation, chat, study access.

2. **GitHub API**: Release checking and update downloading. No authentication (public repo).

3. **KUAL**: Menu integration via JSON configuration. Script-based launching with PID management.

4. **X11**: Direct protocol access via x11rb. No window manager in release builds (`override_redirect`).

### Conventions to Preserve

1. **Environment Variables**: Compile-time `env!()` for paths, not runtime `std::env::var()`
2. **Logging**: Use `log` macros consistently, include context in messages
3. **Error Handling**: Log and continue where possible, never panic in event handlers
4. **Async**: Spawn tasks from event handlers, communicate via channels, never block
5. **Screen Navigation**: Use `Transition` enum, never modify screen_stack directly outside App
6. **Widget Rendering**: Borrow Renderer, never own X11 resources

### Known Limitations

1. **Single Display Size**: Only supports 1072×1448. Other Kindle models would need layout adjustments.
2. **No Test Infrastructure**: No mocking, no test fixtures, no CI pipeline.
3. **No Error Recovery**: Network failures in OAuth or game streams result in screen-level errors, no retry logic.
4. **No Persistent State**: Game state not saved between sessions (except OAuth token).
5. **No Multiplayer UI**: Can receive game events but UI for creating challenges is missing.

### Build & Deployment Complexity

1. **Cross-Compilation**: Requires `cross` and Docker/Podman for `armv7-unknown-linux-musleabi` target
2. **Static Linking**: `RUSTFLAGS="-C target-feature=+crt-static"` for musl
3. **Flash Scripts**: `flash.sh` handles scp to Kindle, preserves `secrets/token.json` across deploys
4. **Update Mechanism**: Two-stage — download to `.new` file, move at next launch

## Recommendations

### Immediate (P0)

1. **Extract screens from `models/ui.rs`**: Move each Screen struct to `ui/screens/{name}.rs` and its impl to `ui/screens.rs` or co-located files.

2. **Add basic unit tests**: Start with `bitboard.rs` — pure logic, easy to test, high value for regression prevention.

### Short-term (P1)

3. **Create consistent error type**: Define a `ChessError` enum that wraps all error variants, implements `Send + Sync + 'static`, and `From<Box<dyn Error>>`.

4. **Add test infrastructure**: Set up `cargo test` with mock HTTP client for API tests.

5. **Extract layout constants**: Move 1072×1448 and derived values to a `layout.rs` module for easier multi-device support.

### Medium-term (P2)

6. **Implement retry logic**: Add exponential backoff for transient network failures, especially in OAuth and game stream.

7. **Add health check endpoint**: For the OAuth callback server, add a `/health` endpoint to verify server is running.

8. **Improve error UI**: Add error message display on screens (toast or modal) instead of just logging.

### Long-term (P3)

9. **Multi-device support**: Abstract screen dimensions, create layouts for different Kindle models.

10. **Persistent game state**: Save/load game state between sessions.

11. **Challenge creation UI**: Add ability to create and send challenges to other users.

## Summary

kindle-chess is a **mature, well-architected Rust application** for a niche platform (jailbroken Kindle). It demonstrates:

- **Strengths**: Clean separation of concerns (App/Screen/Display), excellent type safety with typestate pattern, careful async handling, comprehensive Lichess API integration, robust OAuth flow.
- **Weaknesses**: No test suite, monolithic screen files, hardcoded dimensions, manual error handling at async boundaries.
- **Technical Debt**: Primarily organizational (large files) rather than functional. The code works well and is maintainable.
- **Quality**: Production-ready for its target use case. Would benefit from test infrastructure for long-term maintainability.

The architecture is **sound and scalable** — adding new screens or features follows established patterns. The main risk is the lack of automated testing, which could lead to regressions as the codebase grows.
